## 1. Executive Summary

Phase R4 implements the complete core learning loop of the LMS:
1. Hierarchical content structure: Courses → Modules → Lessons → Materials.
2. Server-side authoritative playback tracking, progress aggregation, and anti-abuse detection.
3. Teacher Course Builder workspace for modules, lessons, and materials management.
4. Distraction-free Student Course Player with playback heartbeats, resume position, materials download, and dynamic anti-piracy watermarking.
5. Removal of the simulated fake AI Tutor (`setTimeout` canned responses) in favor of real, verified learning progress and course catalog navigation.

All implementations strictly adhere to `AGENTS.md`: no mock fallbacks, client is not the security boundary, and all access decisions are enforced by `ContentAccessPolicy` on both streaming embeds and material downloads.

## R4-3a/b/c Platform Drive storage pool, resumable uploads, media workers — 2026-11-19 (ADR-009)

**Status:** PARTIAL (all three; tested with Google faked and the sync queue)

**What was built**
- Super admin `/platform/storage` page and `GET/PUT/DELETE /platform/drive-accounts…`:
  - connect several Google accounts, with Drive-only consent (`openid email drive.file`)
  - see limit, used, reserved and free space
  - refresh the quota
  - pause new uploads
  - reorder accounts
  - disconnect: tokens revoked, the row and the files kept; refused while space is reserved
- Central tables `platform_drive_accounts`, `platform_drive_folders` and `platform_drive_reservations`. Tokens are encrypted and never returned, so a tenant cannot reach them.
- How storage is chosen:
  - An academy with its own Google connection keeps using it.
  - Otherwise the first pool account by priority is used, if its free space (limit − usage − active reservations) covers the file plus `GOOGLE_DRIVE_POOL_MARGIN_BYTES` (1 GiB).
  - Choosing and reserving happen inside one locked transaction, so uploads that start at the same moment cannot overfill an account.
  - A quota older than 10 minutes is read from Google first.
  - When no account has room, the upload is refused with `409 STORAGE_FULL` before any byte is sent, and the refusal is audited.
- Resumable uploads:
  - `GET /media/uploads/{id}` asks Google how many bytes it holds.
  - After a drop, the browser resends only the rest, with back-off, and waits for `online`.
  - After a reload, the pending upload is offered again (stored in `localStorage`); picking the same file resumes it.
- Workers:
  - `complete` answers 202 and `FinalizeMediaUpload` (queue `media`, 5 tries) checks, shares and registers the file, then releases the reservation.
  - `PollDriveVideoProcessing` rechecks for about 24 hours and flips `processing` to `ready`.
  - `lms:refresh-drive-quotas` runs every 15 minutes and releases expired reservations.
  - The Docker worker and the RUNBOOK now use `--queue=media,default`. Without that the media jobs would never run.
- Refactor:
  - `GoogleDriveClient` takes a `DriveAccess` (tenant or pool) on every call.
  - The OAuth state store is shared, and the public callback finishes either flow from the state alone.
- Changes in behaviour:
  - Assets record `metadata.storage`.
  - `complete` can now answer 202.
  - The web client polls until the status is `completed` or `failed`.
